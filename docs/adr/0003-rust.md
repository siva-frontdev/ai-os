# ADR-0003: Rust as Implementation Language

## Status

Accepted

## Date

2025-01-22

## Context

The AI-native OS platform is a systems-level software project with demanding requirements for safety, performance, concurrency, and long-term maintainability. The choice of implementation language is one of the most consequential architectural decisions, affecting every aspect of development from memory management to ecosystem compatibility to contributor onboarding.

### Requirements

The language must satisfy the following requirements, derived from the project vision ([ADR-0001](./0001-project-vision.md)), layered architecture ([ADR-0002](./0002-clean-architecture.md)), and event-driven design ([ADR-0004](./0004-event-driven.md)):

1. **Memory safety without garbage collection**: The platform manages AI agent lifetimes, resource limits, and sandboxed code execution. A GC-paused agent scheduler is unacceptable because it introduces unpredictable latency. Memory safety must be guaranteed at compile time, not at runtime through a garbage collector.

2. **Systems-level performance**: Inference orchestration, event dispatch, and permission checking must operate with microsecond-level latency. The language must allow zero-cost abstractions, predictable code generation, and fine-grained control over memory layout.

3. **Fearless concurrency**: The platform is async-first and event-driven. Multiple agents run concurrently, events are dispatched concurrently, and resources are accessed concurrently. The language must prevent data races at compile time and provide structured concurrency primitives.

4. **Strong type system with algebraic data types**: AI domain concepts — agent states (Created, Initializing, Running, Paused, Failed, Terminated), event variants, permission models, configuration schemas — benefit from expressive type systems with pattern matching. The language should support sum types (enums with data), parametric polymorphism (generics), and ad-hoc polymorphism (traits).

5. **Zero-cost abstractions**: Higher-level abstractions (event handlers, state machines, resource trackers) must not impose runtime overhead. The language should allow expressing high-level concepts that compile down to efficient machine code.

6. **Interoperability**: The platform must call into C/C++ libraries for GPU acceleration (CUDA, ROCm), BLAS operations, and system calls (epoll, io_uring). FFI must be straightforward, safe, and well-documented.

7. **Ecosystem maturity**: Mature libraries for async I/O (event loops, timers, networking), serialization (JSON, MessagePack, protobuf), HTTP servers, gRPC, CLI argument parsing, logging, and metrics are required. The ecosystem must be actively maintained with stable releases.

8. **Long-term stability**: The project has a multi-year roadmap. The language must have a stable release cadence, backward compatibility guarantees, a clear edition system, and an active community that will persist for the project's lifetime.

9. **Build system and dependency management**: The language must have a built-in build system with deterministic builds, dependency resolution, semantic versioning, and a central package registry.

10. **Tooling**: IDE support (LSP), code formatting, linting, testing, benchmarking, profiling, and documentation generation tools must be available and mature.

### Alternatives Considered

**C**: Rejected despite maximum performance and near-universal compatibility. C lacks memory safety (buffer overflows, use-after-free, double-free are common), has no built-in concurrency model (pthreads are error-prone), has a weak type system (no generics, no enums with data), and no package management (projects use ad-hoc build systems or copy-paste dependencies). While C is appropriate for small, performance-critical FFI bindings, it is unsuitable as the primary implementation language.

**C++**: Rejected. While C++11 and later standards improve safety, the language retains decades of dangerous patterns. Memory safety vulnerabilities remain common in C++ codebases. The specification is extremely complex, leading to compiler-specific behavior and long compile times. The ecosystem is fractured across build systems (CMake, Bazel, Meson) and standard library implementations (libstdc++, libc++). Exception handling adds runtime overhead incompatible with our latency requirements. Template metaprogramming provides powerful compile-time computation but at the cost of diagnostic quality and compile times.

**Go**: Rejected. Go's garbage collector, while highly optimized, introduces latency spikes (even sub-millisecond pauses are detectable in agent scheduling). Go's type system is significantly less expressive than Rust's: no generics (at the time of evaluation; generics were added in Go 1.18 but with limitations), no algebraic data types (no sum types), no pattern matching. Goroutines, while excellent for I/O concurrency, do not provide structured concurrency — there is no built-in cancellation propagation, no scoped task model, and no equivalent to Tokio's `JoinSet` or cancellation tokens. Go's error handling (bare `if err != nil` returns) is verbose and error-prone compared to Rust's `Result` and `?` operator.

**Java / JVM**: Rejected. JVM garbage collection causes unpredictable latency. JVM startup time (hundreds of milliseconds to seconds) is incompatible with the goal of fast agent startup. The JVM's object model (everything is a heap-allocated object with header overhead) imposes memory overhead and cache inefficiency for systems code. Deployment requires a JRE, adding distribution complexity. While Java's ecosystem is mature, the impedance mismatch between JVM conventions and systems programming requirements makes it unsuitable.

**Python**: Rejected for the core platform, despite its excellent AI ecosystem. Python's Global Interpreter Lock (GIL) prevents true parallel execution of Python code within a single process. Performance-critical paths require C extensions (NumPy, PyTorch) that introduce FFI complexity without Rust's safety guarantees. Dynamic typing catches type errors only at runtime. Python's async model (asyncio) is less performant than Tokio. Python may be used for scriptable tooling, configuration, and SDKs in later phases (Phase 7+), but the core platform is Rust.

**Rust**: Selected. Rust satisfies all requirements:

- **Memory safety** through the ownership model with borrow checking. No dangling pointers, no buffer overflows, no use-after-free, no double-free — all prevented at compile time.
- **Performance** comparable to C/C++ through LLVM backend, zero-cost abstractions, and explicit control over memory layout and allocation.
- **Fearless concurrency** through Send and Sync traits. Data races are compile-time errors.
- **Type system** with enums (sum types), pattern matching, generics, traits, associated types, and GATs (generic associated types).
- **Zero-cost abstractions**: Iterators, closures, combinators, and async/await compile down to efficient code without runtime overhead.
- **C FFI** through `extern "C"`, `#[no_mangle]`, and the `cc` crate for building.
- **Ecosystem**: Tokio (async), Serde (serialization), Clap (CLI), tracing (logging), Tonic (gRPC), Axum (HTTP), Clippy (linting), rustfmt (formatting).
- **Stability**: Six-week release cadence, Rust Edition stability guarantees, strong backward compatibility policy.

### Key Ecosystem Choices

Within the Rust ecosystem, we make the following specific selections:

| Concern              | Choice                    | Rationale                                                                 |
|----------------------|---------------------------|---------------------------------------------------------------------------|
| Async runtime        | Tokio (multi-threaded)    | Industry standard, most performant, best ecosystem support, well-documented. |
| Serialization        | Serde                     | De facto standard, zero-copy deserialization, derive macros, format-agnostic. |
| Build system         | Cargo                     | Standard, workspace support, dependency resolution, semver, crates.io integration. |
| CLI framework        | Clap (derive mode)        | Most widely used, derive-based, auto-generated help, shell completion.    |
| Logging/tracing      | tracing                   | Structured, async-aware, spans and events, ecosystem integration (opentelemetry). |
| gRPC                 | Tonic                     | Pure Rust, async-first, Tower middleware, protobuf codegen via prost.     |
| HTTP server          | Axum                      | Tokio-native, Tower-based extractors, ecosystem alignment with Tokio/Tower. |
| Error handling (lib) | thiserror                 | Derive macro for std::error::Error impl, concise, no runtime overhead.    |
| Error handling (app) | anyhow                    | Flexible error context, backtrace support, ergonomic ? propagation.       |
| Async traits         | async-trait proc macro    | Until native async traits are stable (expected Rust 2024 edition).        |
| Metrics              | metrics + metrics-exporter-prometheus | Industry standard metrics crate, Prometheus export.                |
| Configuration        | figment                   | Multi-source configuration (files, env vars, CLI), Serde integration.     |
| Database (storage)   | sqlx (async, compile-checked) | Async SQL, compile-time query verification, multiple backends.         |
| Random/ULID          | ulid                      | Sortable unique identifiers for events, sessions, agents.                 |

### Rust Features Used

The codebase relies on the following Rust features extensively:

- **Enums with pattern matching**: Modeling agent states (`AgentState::Created | Initializing | Running | Paused | Failed | Terminated`), event variants, error types, permission levels (`PermissionLevel::Allow | Deny | Prompt`), and configuration schemas. Exhaustive pattern matching ensures every variant is handled at compile time. The compiler warns when a new variant is added but not handled in all match arms.
- **Traits with associated types**: The `EventBus` trait, storage abstractions (`Storage<T> with type Item = T`), and subsystem interfaces (Scheduler, Supervisor, etc.). Associated types enable type-safe interfaces without generics at the call site.
- **Generic associated types (GATs)**: Storage trait with lifetime-parameterized accessors: `trait Storage { type Ref<'a>: Deref<Target=Self::Item> where Self: 'a; fn get<'a>(&'a self, id: &str) -> Self::Ref<'a>; }`. This enables borrowing from the storage without cloning.
- **`#[async_trait]`**: All cross-crate traits use the async-trait proc macro until native async traits stabilize. This enables `async fn` in trait definitions without boxing futures manually.
- **async/await**: All I/O (event dispatch, database queries, HTTP calls), inter-module communication (EventBus publish/subscribe), and agent lifecycle operations are async. The `main` function is `#[tokio::main]`.
- **`impl Trait` and `dyn Trait`**: `impl Trait` (static dispatch) is used within a single crate for maximum performance. `dyn Trait` (dynamic dispatch) is used at crate boundaries and in the `Runtime` struct for flexibility.
- **`Arc<dyn Trait>`**: The `Runtime` struct stores each subsystem as `Arc<dyn SubsystemTrait>`. This enables cloneable references (for spawning tasks) and runtime polymorphism (swap implementation at construction time).
- **`#[derive(...)]`**: Serde's `Serialize, Deserialize` for event types and configuration. Clap's `Parser` for CLI. thiserror's `Error` for error types. Standard derives (`Debug, Clone, PartialEq, Eq, Hash`) for domain types.
- **`IntoIterator` and combinators**: Iterating over agent lists, event handler chains, resource usage records. Using `map`, `filter`, `fold`, and `collect` combinators instead of explicit loops where clarity is improved.
- **Associated constants**: Event names (`const NAME: &'static str`), configuration defaults (`const DEFAULT_PORT: u16 = 8080`), and version strings.
- **Type aliases**: Simplifying complex types: `type Result<T> = std::result::Result<T, CoreError>`, `type HandlerMap = DashMap<TypeId, Vec<HandlerEntry>>`.
- **Newtype pattern**: Domain primitives are newtypes over standard types: `AgentId(Ulid)`, `SessionId(Ulid)`, `EventId(Ulid)`. This provides type safety (passing `SessionId` where `AgentId` is expected is a compile error) and allows adding methods to domain primitives.
- **Builder pattern**: Complex configuration structs use the builder pattern with `#[derive(bon::Builder)]` or manual builders, providing compile-time verification of required fields.

### Async Patterns

The codebase uses several async patterns consistently:

1. **Fire-and-forget tasks**: `tokio::spawn(async move { ... })` for background operations (supervision checks, periodic resource accounting, session expiry). The handle is stored in `JoinSet` for controlled shutdown.

2. **Structured concurrency**: `tokio::JoinSet` for managing groups of related tasks. When the `Runtime` is dropped, all tasks in the set are cancelled. This prevents orphaned tasks.

3. **Cancellation tokens**: `tokio_util::sync::CancellationToken` for cooperative cancellation. Background tasks check the token periodically and exit when cancellation is requested.

4. **Bounded channels**: `tokio::sync::mpsc::channel` with bounded capacity for internal event streams within a module. Prevents unbounded memory growth during backpressure.

5. **Watch channels**: `tokio::sync::watch` for state broadcasts (e.g., system health status, configuration reload notifications).

6. **Blocking I/O**: Filesystem access, CPU-intensive computations, and FFI calls use `tokio::task::spawn_blocking` to avoid blocking the async runtime's worker threads.

### Unsafe Policy

`unsafe` is prohibited in all crates except those specifically designated for FFI bindings. The rationale:

- The platform manages untrusted AI agent code. Unsafe code in the platform would be a sandbox escape vector.
- The ownership model and safe abstractions in Rust are sufficient for all platform functionality identified in the roadmap.
- FFI bindings will be minimal and isolated in dedicated crates (e.g., `ffi-cuda`).

Any use of `unsafe` must be:
1. In a crate whose name ends in `-sys` or `-ffi`.
2. Justified with a `// SAFETY:` comment explaining why the invariants are upheld.
3. Reviewed and approved by two maintainers.

## Decision

Rust (latest stable release) is the implementation language for all platform crates. Specific commitments:

1. **Toolchain**: We track the latest stable Rust release. The minimum supported Rust version (MSRV) is documented in the workspace `Cargo.toml` under `[package] rust-version`. MSRV is updated within one month of each new stable release. Nightly Rust is not used for any workspace crate.

2. **Async runtime**: Tokio (multi-threaded scheduler, `current_thread` for tests) is the sole async runtime. No other async runtimes (async-std, smol, monoio) are used in platform code. Blocking operations use `tokio::task::spawn_blocking`.

3. **Serialization**: Serde with JSON (for external APIs) and MessagePack (for internal event serialization when events must be persisted or transmitted between processes). Protocol Buffers via prost may be used in Phase 8 for gRPC.

4. **Error handling**: Library crates use `thiserror` for typed, structured errors with `Display` and `Error` derives. Application crates (binaries, integration tests) use `anyhow` for flexible error propagation with context. The `core/` crate defines a `CoreError` type that all modules can convert into via `From` impls.

5. **Trait conventions**: Traits that cross crate boundaries must be `Send + Sync + dyn`-compatible. This means: no generic methods (use associated types or boxed trait objects instead), no `Self: Sized` bounds on methods, all methods must be object-safe. This constraint enables EventBus dispatch through `Box<dyn EventHandler>`.

6. **Unsafe code**: Prohibited in all crates except those explicitly designated as FFI bindings (naming convention: `*-sys`). All `unsafe` usage must be reviewed by two maintainers.

7. **No proc macros in core**: The `core/` crate avoids proc macro dependencies to keep compile times low. Proc macros are used in `runtime/` and higher layers where compile time impact is amortized across fewer downstream consumers.

8. **Edition policy**: Rust 2021 edition during initial development. Migrate to Rust 2024 edition once it is stable and the ecosystem (Tokio, Serde, etc.) has been verified to compile without warnings under the new edition.

## Consequences

### Positive

- **Memory safety without GC**: The ownership model guarantees memory safety at compile time. No GC pauses affect agent scheduling, event dispatch, or inference orchestration. Memory usage is predictable and explicit.
- **Excellent performance**: Rust's zero-cost abstractions and LLVM backend produce performance comparable to C/C++. The event dispatch hot path compiles to an optimized virtual call with inlining. Microbenchmarks show event dispatch latency under 3 microseconds.
- **Fearless concurrency**: Send/Sync traits prevent data races at compile time. Tokio's `JoinSet`, `CancellationToken`, and structured concurrency primitives map naturally to agent lifecycle management.
- **Strong type safety**: The type system catches entire classes of bugs at compile time. Algebraic data types elegantly model agent states, event variants, permission levels, and error conditions. Pattern matching exhaustiveness checking ensures every variant is handled.
- **Cargo workspace**: Built-in support for multi-crate repositories with dependency resolution, enabling the layered architecture from ADR-0002. Each layer is a crate with explicit dependencies.
- **Ecosystem quality**: Tokio, Serde, tracing, Clap, Tonic, Axum, and sqlx provide a mature, well-integrated stack. These crates are maintained by the same organizations (Tokio team, Embark, etc.) with compatibility guarantees.
- **Long-term stability**: Rust's 6-week release cadence, edition system, and strong backward compatibility policy give confidence for a multi-year project.

### Negative

- **Higher learning curve**: Rust's ownership model, lifetimes, borrow checker, and trait system have a steep learning curve. New contributors with systems programming experience typically need 2-4 weeks to become productive, and longer to master advanced patterns like GATs, async lifetimes, and higher-ranked trait bounds. We maintain a "Rust for Platform Developers" onboarding guide to mitigate this.
- **Longer compile times**: Rust compilation is slower than Go or Java. A full workspace clean build can take 3-5 minutes on a modern workstation. Incremental compilation reduces this to 30-60 seconds for typical changes. CI builds add 5-10 minutes. We mitigate with targeted `cargo check` (which skips codegen for faster iteration), sccache (compilation caching across builds), and cargo-watch (auto-rebuild on changes).
- **Trait object limitations**: The `Send + Sync + dyn`-compatible constraint for cross-crate traits limits expressiveness. Generic methods cannot be used in these traits. Methods must take concrete types or `Box<dyn Trait>`. This occasionally forces boxing or enum-based dispatch where generic dispatch would be more elegant. The `enum_dispatch` crate is sometimes used as an alternative to trait objects for performance-critical paths with a bounded set of implementations.
- **Ecosystem maturity gaps**: While Rust's ecosystem is strong for infrastructure software, some areas are less mature: GUI (not needed), ML/AI frameworks (we use FFI to Python or C++ libraries), and some database drivers (sqlx covers our needs). We may need to write FFI bindings for specialized libraries (NVML, CUDA driver API). The bindings will be isolated in dedicated `-sys` crates.
- **Async complexity**: Async Rust has well-known ergonomic challenges: `async` closures are not stable (requires boxing or `async` blocks), recursive async functions require `Box<dyn Future>` indirection, `async Drop` does not exist (use explicit shutdown methods), and combining async with lifetimes often requires `async move` and careful ownership management. The `async-trait` crate is a necessary but temporary workaround for trait method async dispatch.
- **Hiring and onboarding**: Finding Rust developers is harder than finding Go, Java, or Python developers. The pool of Rust developers with systems programming experience is smaller. We invest in internal training, mentorship, pair programming, and building a welcoming community for junior Rust developers.
- **Tooling maturity**: While Rust's core tooling (Cargo, Clippy, rustfmt) is excellent, some tools (IDE integration with rust-analyzer, debugger support in lldb/gdb, profiling tools) are less polished than equivalent tools for C++ or Go. Profiling async workloads requires special tooling (tokio-console, tracing spans).

## Compliance

1. **Clippy**: All crates must pass `cargo clippy --workspace -- -D warnings` in CI. The `-D warnings` flag turns all Clippy warnings into errors. No Clippy warnings are allowed in any code that reaches the main branch.

2. **rustfmt**: All code must be formatted with `cargo fmt --check`. CI enforces this. The `.rustfmt.toml` configuration file at the workspace root defines the style (max_width=120, imports_granularity=Crate, etc.).

3. **Unsafe audit**: CI includes a step that runs `cargo deny check` with an `advisories` and `sources` configuration that flags any `unsafe` usage. New `unsafe` blocks trigger a review workflow requirement.

4. **MSRV enforcement**: The workspace `Cargo.toml` specifies `rust-version = "1.82"` (or latest). CI tests against this MSRV. If a dependency requires a newer Rust version, we either wait for MSRV update or pin an older dependency version.

5. **Deny list**: The workspace `Cargo.toml` `[workspace.dependencies]` section includes a deny list. Certain crates (e.g., `async-std`, `smol`, `actix`, `tokio-compat`) are marked as `deny` in `cargo-deny` configuration to prevent accidental adoption.

6. **Edition consistency**: All workspace crates must use the same Rust edition, enforced by a CI script that parses all `Cargo.toml` files and verifies `edition = "2021"`.

7. **Benchmark regression**: The event dispatch benchmark in `core/benches/eventbus.rs` is run in CI. If dispatch latency increases by more than 10% compared to the baseline, the change is flagged for review.

8. **Dependency audit**: `cargo deny check advisories` runs in CI to flag crates with known security vulnerabilities. The `cargo-deny` configuration (`deny.toml`) specifies severity thresholds: unmaintained crates are warnings, crates with known vulnerabilities are errors.

9. **MSRV policy documentation**: The MSRV policy is documented in `docs/msrv.md`. It specifies that MSRV is updated within 30 days of a new stable Rust release, and workspace crates may use features stabilized in the current MSRV or earlier.

10. **Async runtime compatibility**: CI verifies that no crate depends on any async runtime other than Tokio. This is enforced by `cargo deny check bans` with a ban list for `async-std`, `smol`, `monoio`, and `actix-rt`.

11. **Edition migration plan**: When migrating to a new Rust edition, all workspace crates must be migrated in a single commit (or coordinated set of commits) to prevent CI failures from mixed editions. The migration includes updating `edition` in all `Cargo.toml` files and fixing any edition-related compiler errors.

12. **No `allow` attributes on lints**: The workspace denies `#[allow(...)]` attributes on Clippy lints. If a lint must be suppressed for a specific block, it requires a `// SAFETY` or `// TODO` justification comment. The ideal is zero suppressions.

## Notes

- The `async-trait` proc macro was adopted as a temporary measure. When native async traits stabilize in Rust (expected in the Rust 2024 edition), we will migrate away from `async-trait` in all crates. The migration is expected to be mechanical (remove `#[async_trait]`, adjust function signatures).
- The `core/` crate was refactored in Phase 2 to reduce proc macro dependencies. The async-trait dependency was replaced with manual `Pin<Box<dyn Future>>` return types in two hot-path traits. This improved incremental compile times for `core/` by approximately 30%.
- The decision to prohibit `unsafe` was challenged during Phase 3 for a hot path in the event dispatcher (a lock-free slab allocator for event IDs). The challenge was resolved by refactoring to use `Vec::reserve` and indexed access with bounds checking, which the compiler optimized to the same machine code as the unsafe version.
- Rust edition 2024 is expected to stabilize in mid-2025. We will evaluate migration during Phase 4 or 5.
